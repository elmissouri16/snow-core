# Documentation style guide

This guide defines the visual and structural conventions for every document in
the snow-core repository. All documentation — the project `README.md`, this
`docs/` directory, and `IMPLEMENTATION.md` — must follow these rules so the set
reads as one cohesive, professional publication.

> **Audience:** documentation contributors and agents that rewrite or extend
> Snow's guides. If you are reading a guide for product help, start at the
> [documentation index](README.md).

## 1. Document anatomy

Every document follows the same skeleton, top to bottom:

1. **Title** — one `# Heading` with the document name in Title Case
   (`# Using Snow`, `# Security model`). No numbering (`1.`), no leading
   emoji, no trailing punctuation.
2. **Intro paragraph** — two to four sentences stating what the document
   covers, for whom, and where related material lives. Plain prose; no header
   for the intro itself.
3. **Status or scope note** (optional) — a single `> **Note:**` blockquote
   when the reader must know about pre-alpha status, trust boundaries, or
   scope limits before continuing.
4. **On this page** — a table of contents for documents longer than ~120
   lines. One link per `##` section, using GitHub anchor links. Skip the TOC
   for short documents.
5. **Sections** — `##` for top-level sections, `###` for subsections, `####`
   only when a subsection genuinely needs it. Prefer depth ≤ 3.
6. **Related documents** — the final section, titled exactly
   `## Related documents`, listing two to five relevant guides or references
   as a bulleted list. Every guide ends with this section.

### GitHub anchor links

Anchors are generated by GitHub from headings: lowercase, punctuation and
backticks stripped, spaces replaced with hyphens. For example, `## On this
page` becomes `#on-this-page`, and `### ask_user host interaction` becomes
`#ask_user-host-interaction`. When you rename a heading, check every in-repo
link that points to it and update the anchor.

## 2. Headings and prose

- Sentence case for all `##`–`####` headings: `## Runtime modes`, not
  `## Runtime Modes`. Keep proper nouns (`TUI`, `SDK`, `Go`, `Agent Skills`,
  `OpenCode Go`) capitalized as-is.
- Wrap prose at 80 columns. One blank line before and after every block
  element (headings, code blocks, tables, lists, blockquotes).
- Active voice and imperative mood for procedures: "Run `snow login`",
  not "The command should be run".
- One idea per paragraph. Prefer short paragraphs over walls of text.
- Use `1.`, `2.` numbered lists only for ordered procedures; use `-` bullets
  for everything else. Indent continuation lines by two spaces.
- No emojis, no `---` horizontal rules inside a document, no raw HTML.
- Never use bold text as a pseudo-heading (`**Install:** ...`). If it deserves
  a heading, make it a heading.

## 3. Admonitions

GitHub-flavored blockquotes with a bold lead-in label. Use exactly these four
kinds, and use them sparingly:

| Kind | Markup | When to use |
|---|---|---|
| Note | `> **Note:**` | Neutral clarification, scope limit, pre-alpha status |
| Tip | `> **Tip:**` | Best practice, shortcut, recommended workflow |
| Warning | `> **Warning:**` | Security boundary, credential handling, data loss, breaking change |
| Caution | `> **Caution:**` | Destructive or irreversible operation |

Example:

```markdown
> **Warning:** Auth files are written with `0600` permissions. Never print a
> credential value in logs, errors, or tool output.
```

## 4. Tables

Use tables for reference data: flags, commands, configuration keys, provider
catalogs, event types. Rules:

- Always include a header row and a `---` separator row.
- Keep tables under six columns; split the table when it gets too wide.
- Keep cells short. Multi-sentence cells belong in prose, not in a table.
- Use backticks for code, flags, and paths inside cells.
- Align prose cells left (default). No alignment markers needed.

## 5. Code blocks

- Always fence code with a language tag: `sh`, `go`, `json`, `yaml`,
  `python`, `javascript`, `typescript`, `text`.
- Shell blocks are copy-paste ready: no `$` prompt prefixes. State where
  commands run (for example, "from the repository root") in the prose before
  the block.
- Use `text` for terminal output and `json` for JSON fragments.
- Omit nonessential output; use `...` on its own line to elide.

Example:

```sh
go build ./cmd/snow
./snow -p "list files"
```

Inline code covers commands (`snow resume`), flags (`--permission`), files
(`~/.snow/config.json`), packages (`pkg/snowsdk`), and env vars
(`OPENCODE_API_KEY`).

## 6. Links and terminology

- Relative links for everything inside the repository, including anchors:
  `[Configuration](configuration.md)`, `[README](../README.md#quick-start)`.
- External links use descriptive text with the full `https://` URL. Never
  leave bare URLs in prose.
- Product terminology is fixed:
  - **snow-core** — the repository/project name.
  - **Snow** — the product, the binary `snow`.
  - Provider IDs in backticks: `opencode-go`, `chatgpt`, `fake`,
    `openai-compatible`.
  - Paths in backticks: `~/.snow/config.json`, `internal/agent`.
  - Versionless package names: `pkg/snowsdk`, `pkg/protocol`.
- Spell out acronyms on first use in each document: "Model Context Protocol
  (MCP)".

## 7. Consistency checklist

Before finishing any document, verify:

- [ ] Exactly one `#` title; sentence-case `##` headings; depth ≤ 3.
- [ ] TOC present for documents over ~120 lines; anchors match GitHub slug
      rules.
- [ ] Prose wrapped at 80 columns; blank lines around blocks.
- [ ] Tables have header separators and ≤ 6 columns.
- [ ] Code blocks carry language tags and no `$` prefixes.
- [ ] Admonitions use the four approved kinds only.
- [ ] Every relative link resolves; anchors still match renamed headings.
- [ ] All technical facts, commands, flags, schema fields, and URLs from the
      previous version were preserved or corrected against source.
- [ ] Ends with `## Related documents`.
- [ ] No trailing whitespace; file ends with a newline.
