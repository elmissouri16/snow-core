# Publish an end-user-only Snow documentation site

Written against: 10b105d694b7ce205c652462f9a422c9da7996cc

## Evidence chain

- Surface: `https://elmissouri16.github.io/snow-core/`, `/`, the shared sidebar, and the public guide set generated by `.github/workflows/pages.yml`
- Problem: The live `/snow-core/` page currently renders `docs/README.md`, whose first paragraph describes the repository documentation directory and whose sections expose maintainer design history, release machinery, performance work, implementation plans, and canonical repository ownership. This is not an organized first-use path for someone trying to install Snow and use its agents. The intended generated landing page also links contributors to the complete internal index and promotes release preparation beside user workflows.
- Design evidence: The user explicitly requires the Pages site to serve people using Snow rather than repository internals. `docs/pages.md` defines GitHub Actions as the required publishing source and identifies `site/index.md`, `site/_layouts/home.html`, and `site/_includes/navigation.html` as the presentation owners. The current live response proves that branch publication is bypassing that generated surface. `site/index.md` and `site/_includes/navigation.html` then prove that the intended surface still exposes “Contributors,” “Release policy,” and “All documentation.” `scripts/build-pages.sh` proves that every tracked `docs/*.md` file plus `README.md`, `IMPLEMENTATION.md`, `AGENTS.md`, `CHANGELOG.md`, CI workflow files, and benchmark configuration is copied into the public artifact.
- Owner: `site/index.md`, `site/_layouts/home.html`, `site/_includes/navigation.html`, and the publication allowlist in `scripts/build-pages.sh`
- Scope and affected surfaces: Pages source configuration; the `/` landing page; desktop and mobile navigation; a new `/docs/getting-started.html` guide; the public guide artifact; public SDK/example/schema routes; the 404 page; repository-only documentation ownership records; Pages tests and rendered-link validation
- Uncertainty: GitHub’s repository setting cannot be changed by a source commit. A repository administrator must confirm that **Settings → Pages → Source** is `GitHub Actions`; the implementation must stop if that setting cannot be changed.

## Design decision

Treat the GitHub Pages artifact as an end-user product manual, not as a mirror of repository documentation. Keep maintainer, research, audit, release-process, architecture, benchmark, workflow, and historical implementation documents in the repository, but do not stage or link them in the public Pages artifact.

Give the public site one ordered task path: install Snow, run a first agent prompt, configure a provider and permissions, learn daily workflows, extend the agent, and integrate through supported public APIs. Preserve the existing Snow visual identity and layouts; change information architecture and copy rather than replacing the design system.

The GitHub repository README must remain useful as a repository landing page, but Pages must not publish the complete README. Create a dedicated canonical getting-started guide from the existing user-facing Quick Start material so the public install route does not expose the README’s contributor and implementation sections.

## Reuse

- `site/_layouts/default.html` for every guide page
- `site/_layouts/home.html` for the public landing composition
- `site/_includes/navigation.html` as the only desktop/mobile navigation owner
- Existing `feature-grid`, `feature-card`, `hero-actions`, `primary`, `secondary`, `eyebrow`, `prose`, and responsive rules in `site/assets/css/style.css`
- Existing canonical user guides: `docs/using-snow.md`, `docs/configuration.md`, `docs/chatgpt-auth.md`, `docs/sessions.md`, `docs/plan-mode.md`, `docs/goals.md`, `docs/subagents.md`, `docs/skills.md`, `docs/mcp.md`, `docs/plugins.md`, `docs/security.md`, `docs/sdk.md`, `docs/rpc.md`, `docs/user-input.md`, and `docs/plugin-protocol.md`
- Existing public integration aliases and artifacts under `site/examples/`, `site/pkg/`, `examples/sdk/`, and `pkg/protocol/schema/rpc/v1/`
- Exemplar: the current “Get started,” “Core workflows,” and “Integrate” grouping in `site/_includes/navigation.html`, retained structurally but rewritten around external-user tasks

No new visual primitive is required. The current hero, cards, navigation groups, content layout, tokens, and responsive behavior can express the selected information architecture.

## Scope

- Inherit: Desktop sidebar, mobile disclosure navigation, homepage hero/cards, every retained public guide using the default layout, the Pages workflow, and future Pages builds using the explicit allowlist

## Stop conditions

- Stop if GitHub Pages cannot be configured to use GitHub Actions, because branch deployment cannot render the repository’s intended staged site.
- Stop if a retained public guide requires an excluded file for executable examples or public API semantics; classify that dependency as user-facing and add only that specific file after documenting why, rather than restoring a broad glob.
- Stop if moving first-run ownership out of the README would leave GitHub visitors without a copyable install path; retain a concise install block in README while keeping the complete sequence canonical in `docs/getting-started.md`.

## Design documentation

- After acceptance and validation: record in `docs/pages.md` that GitHub Pages is a curated end-user manual built from an explicit allowlist, while `docs/README.md` remains the complete repository/maintainer index; record `docs/getting-started.md` as the canonical first-run owner in `docs/README.md` and `IMPLEMENTATION.md`.
